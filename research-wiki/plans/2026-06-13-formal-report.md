# 招标文书 AI 审查系统 — 内测成果与正式版建设方案

## 一、产品概述

招标文书 AI 审查系统是一款面向法律从业者的智能审查工具，旨在辅助律师高效完成招标采购文书的合规性审查工作。

在传统工作模式中，律师需要逐条对照法规和行业指引，人工审阅招标文书中的资格条件、评分标准、合同条款等内容，判断是否存在违规或不当之处。一份完整的招标文书通常数十页至数百页，涉及的审查要点多达百余条，单个项目的人工审查往往需要数天时间。当多个项目同时进行时，人力瓶颈尤为突出。

本系统的工作模式为：律师上传招标文书及相关补充文件，选择适用的审查标准（审核点），系统即自动对文书内容逐点进行合规性审查。每个审核点的审查过程包括：在文书中检索相关内容、比对法规要求、判定合规性、提取原文证据、引用法条依据。审查完成后，系统生成包含上述全部信息的结构化审查工作底稿（Word 格式），律师在此基础上复核修订并定稿输出。

系统采用三层技术架构：底层为自研的混合检索引擎，负责对文书内容进行语义检索和关键词匹配；中间层为通用的 AI 智能体编排框架，负责协调大语言模型完成多步骤推理任务；顶层为面向招标审查业务的应用系统，包含文档管理、审核点管理、审查任务调度、结果展示和底稿生成等完整业务功能。

## 二、内测阶段成果

系统已完成内测版的开发与部署，建立了从文档上传到底稿输出的完整业务闭环，并已在真实招标项目中投入试用。以下从核心能力和运行数据两个维度汇报内测阶段的主要成果。

### 2.1 已建成的核心能力

系统已实现的完整工作流程为：上传招标文书 → OCR/文档智能转换 → 配置审核点和审核点库 → 发起 AI 审查任务 → 查看审查结果 → 编辑修订工作底稿 → 定稿导出 Word → 回灌案例库。各环节的具体能力如下：

| 能力 | 说明 |
|---|---|
| 文档智能转换 | 支持 PDF、DOCX、DOC 三种主流文档格式上传。上传后系统自动调用 OCR 服务将文档转换为可检索的结构化 Markdown 文本，支持扫描件 PDF 的文字识别。转换完成后文档进入文档库，可在后续审查和对比任务中反复使用 |
| 审核点库管理 | 支持通过 Excel 表格批量导入审核点，每个审核点包含标题、审查描述、严重程度、法条依据、关键词等字段。审核点按库进行组织管理，支持标签分类和搜索筛选。目前已建立 185 个标准审核点，覆盖政府采购和工程招标的主要合规要点 |
| AI 逐点审查 | 基于大语言模型对招标文书逐审核点进行合规性审查。每个审核点的审查流程为三阶段式：首先制定审查计划（确定需要在文书中查找的内容），然后执行检索和分析（在文书中定位相关段落并进行合规性判断），最后生成结构化审查结论（包含合规/不合规/存疑的判定、问题描述、原文证据摘录和法条依据引用） |
| 工作底稿生成 | 全部审核点审查完成后，系统自动汇总各点的审查结论，生成规范化的审查工作底稿（Word 格式）。律师可在系统内对底稿内容进行修订，修改审查结论、补充意见或标记误报，修订完成后定稿导出。支持部分审核点失败时仍生成残缺底稿，失败点可单独重试或跳过 |
| 文档对比分析 | 支持多个文档之间的相似度对比分析，可识别文档间完全重复、高度相似和疑似抄袭的内容段落。对比结果按相似度分类展示，支持上下文查看和结果筛选。适用于识别不同招标项目间文书雷同的场景 |
| 案例库积累 | 定稿后的审查结果自动回灌案例库，形成可检索的审查经验积累。后续审查任务可参考历史案例，持续提升审查的一致性和准确性 |

## 三、正式版建设方向

内测版已验证了"AI 辅助合规审查"技术路线的可行性，并在真实项目中积累了运行数据和用户反馈。但内测版本质上是技术验证原型——单用户模式运行，不具备用户身份管理、数据权限隔离和多人并发使用的能力。要将其建设为可供十余名律师日常使用的正式版产品，需要在底层数据架构、任务调度引擎和业务功能三个层面进行全面重构，核心升级方向为：**更稳定、更高效、更准确**。

### 3.1 更稳定

内测版作为技术验证原型，在长时间运行和异常处理方面存在不足。正式版需确保多用户日常使用中系统可靠运行、故障可恢复、状态可追溯。

**用户体系与数据隔离**：内测版无登录机制，所有用户共用同一身份、看到同一份数据。正式版需建设完整的用户登录、角色权限和数据隔离体系——每位律师只能看到自己有权限的文档、审查任务和工作底稿，管理员可管理本组织内的用户和共享资源。这是多人正式使用的最基本前提，涉及底层数据模型的全面重构：现有的文档、审查任务、审核点、工作底稿等全部业务表都需要增加归属字段（所属用户、所属组织），全部 API 接口都需要增加权限校验逻辑。

**任务可靠性**：内测版的后台任务（文档转换、AI 审查、文档对比）运行在应用进程内部，如果服务重启，正在执行的任务会直接丢失，需要技术人员手动介入恢复。在一次实际部署更新中，就曾因服务重启导致 3 个正在执行的审查任务中断。正式版需要建设持久化的任务队列和心跳监控机制，确保任务在服务重启后能自动恢复，长时间无响应的任务能被检测并报警。

**错误处理与可观测性**：内测版对外部服务（OCR 服务、大语言模型接口）的异常处理较为简单，服务不可用时可能静默失败或返回不明确的错误。正式版需要建设健康检查机制，对 OCR 服务、大语言模型接口、数据库等关键依赖进行持续监控；对失败操作提供明确的错误提示和重试入口；对关键业务操作（上传、删除、编辑、定稿、导出）全程记录审计日志，支持操作追溯。

| 当前状况 | 正式版要求 |
|---|---|
| 单用户模式，无登录和权限控制 | 完整的用户体系、角色权限和多租户数据隔离 |
| 全部业务表无归属字段 | 数据模型全面重构，增加用户/组织/项目归属 |
| 进程重启可能丢失进行中的任务 | 持久化任务队列，重启后自动恢复 |
| 长时间审查任务中断后需技术人员介入 | 心跳监控 + 自动检测异常 + 用户可见状态提示 |
| OCR 和大语言模型服务不可用时静默失败 | 健康检查、自动重试、明确的错误提示 |
| 操作无审计记录 | 关键操作全程留痕，可追溯、可审计 |
| 异常排查依赖技术人员直接查看数据库 | 管理后台可查看系统状态和异常任务 |

### 3.2 更高效

内测版受限于串行处理架构和单机资源调度，处理效率存在明显瓶颈。正式版需通过并发优化和架构改造大幅提升处理速度，满足多用户同时使用的需求。

**AI 审查并行化**：这是效率提升最关键的一环。内测版中，每个审查任务的 134 个审核点严格按顺序逐个执行，每个审核点需经历"制定计划 → 执行检索分析 → 生成结论"三个阶段，单点耗时约 5-15 分钟，整个任务串行执行需要 7-47 小时。正式版需要在大语言模型接口允许的并发范围内，将审核点改为受控的批量并行执行（例如同时处理 3-5 个审核点），预计可将单任务耗时从平均 23 小时缩短至 3-5 小时。同时需要引入令牌桶等流量控制机制，避免并发请求超出大语言模型服务端的承载能力。

**文档转换排队与并发**：内测版的文档转换没有排队机制，多个用户同时上传时，所有转换请求直接并发发送到 OCR 服务，既可能超出 OCR 服务的并发限制导致失败，也无法让用户了解排队进度。正式版需要建设转换任务队列，控制并发数量，并在前端实时展示转换进度和排队位置（例如"排队第 3 位，预计等待 15 分钟"）。

**大文件处理能力**：内测版在处理大文件时将整个文件读入内存，对于数百 MB 的大型 PDF 文件存在内存压力。正式版需要改为流式处理，稳定支持 1 GB 级别的文件上传和转换。

**多用户资源调度**：当十余名律师同时使用系统时，可能同时发起多个审查任务、多个文档转换和多个对比任务。内测版没有全局的资源调度能力，正式版需要建设统一的任务队列和优先级调度机制，确保各用户的任务公平分配系统资源，避免单个大任务阻塞其他用户。

| 当前状况 | 正式版要求 |
|---|---|
| 审查点逐个串行执行，134 个审查点需 7-47 小时 | 受控并行执行，目标缩短至 3-5 小时 |
| 文档转换无排队机制，多人上传互相阻塞 | 转换任务排队、并发控制、进度实时可见 |
| 大文件整文件读入内存处理 | 流式处理，稳定支持数百 MB 至 1 GB 级文件 |
| 多用户同时操作无资源调度 | 统一任务队列和优先级调度，避免互相抢占 |
| 文档检索受限于单机嵌入式引擎 | 提升检索引擎的并发能力和语义匹配精度 |

### 3.3 更准确

内测版在审查结果的准确性和可追溯性方面存在优化空间。正式版需强化从文档转换到审查输出的全链路数据质量，提升审查结果的可信度和实用性。

**OCR 质量提升**：文档转换是审查准确性的源头。内测版的 OCR 结果中存在若干质量问题：部分扫描件 PDF 转换后出现乱码或漏字；页眉、页脚、页码等重复出现的内容未被过滤，干扰 AI 对正文内容的理解；表格结构在转换过程中可能丢失。正式版需要在 OCR 转换后增加文本清洗管线，过滤重复页眉页脚、修正常见乱码模式、检测并提示转换质量异常的文档。

**证据溯源精确化**：内测版的审查结果中包含原文证据的文本摘录，但缺少精确到页码和段落的定位信息。律师在复核时需要手动在原文中查找对应段落。正式版需要建设页码/段落级的证据溯源能力，支持律师在审查结果中点击证据即可跳转到原文对应位置，并高亮显示引用的文本段落。

**AI 提取能力完善**：除了人工导入审核点外，系统还具备从法规指引中自动提取审核点的 AI 能力。内测版的 AI 提取功能在真实文件上的稳定性尚需优化，包括文件解析流程、大语言模型输出格式处理和提取结果的人工确认机制。正式版需要完善 AI 提取的全流程，使其成为审核点库建设的可靠辅助手段。

**算法质量保障体系**：内测版缺少固定的评测基线，算法改动（如调整审查提示词、更换大语言模型版本、优化检索策略）后无法量化评估效果变化。正式版需要建立标准评测数据集和自动化评测流程，确保每次算法迭代都有可量化的质量回归数据支撑。

| 当前状况 | 正式版要求 |
|---|---|
| OCR 转换结果存在乱码、重复页眉页脚等噪声 | OCR 后清洗管线和质量检测 |
| 审查证据基于文本匹配，缺少精确定位 | 页码/段落级证据溯源，支持点击跳转和高亮 |
| AI 审核点提取功能在真实文件上待完善 | 优化文件解析流程、输出处理和人工确认机制 |
| 文档对比结果存在乱码和噪声干扰 | OCR 清洗和异常字符过滤 |
| 无固定评测基线，算法改动无法量化效果 | 建立标准评测集，支持审查质量的量化回归 |

## 四、正式版建设范围

正式版建设涉及 8 个功能模块的全面重构与新增建设，共约 250 项功能点。按业务优先级分为三档：

- **P0**（阻塞正式使用）：用户体系、数据隔离、核心业务闭环等必须具备的能力
- **P1**（影响使用效率）：直接影响律师日常工作效率和业务效果的功能
- **P2**（体验增强）：提升管理效率和使用体验的增强功能

以下对各模块的建设内容做简要说明：

**用户体系与数据隔离（28 项）**：这是正式版最基础也是改动最深的模块。需要从零建设用户注册登录、会话管理、角色权限（普通律师/管理员）体系，并在现有全部数据表上增加用户归属和组织归属字段，实现全部 API 接口的权限校验。每个列表接口需增加权限过滤，每个详情接口需增加可见性校验，每个写入接口需增加操作权限校验——这意味着现有的全部后端接口都需要改造。

**审核点与标签体系（48 项）**：审核点是系统的核心业务数据，正式版需要围绕审核点建设完整的生命周期管理能力。包括：审核点的共享/个人作用域（共享审核点由管理员维护，普通用户可复制为个人版本后修改）；审核点版本控制（修改后生成新版本，历史任务保持旧快照不受影响）；审核点库的权限管理（共享库/个人库）；通用标签体系（可贴到文件、项目、任务、审核点等多种业务对象上）；AI 辅助提取审核点的完善。

**文档管理与转换（37 项）**：正式版需要重构文件存储模型，将物理文件（FileBlob）与用户可见的文件记录（DocumentAsset）拆开，实现文件去重（同一文件多次上传只存一份，共享 OCR 结果）、文件权限（个人文件/项目文件/共享文件）。OCR 转换需要引入排队和并发控制机制。审核点的 Excel 导入需要接入权限和租户体系，并完善冲突处理（与已有审核点重复时的合并/跳过/新建策略）。

**AI 审查引擎（28 项）**：需要将审查任务从单用户模式改造为多租户模式（任务必须属于创建人和组织），引入审核点快照机制（创建任务时固化审核点内容，后续修改不影响进行中的任务）。核心改造是将审查点的串行执行改为受控并行，并建设任务级别的进度追踪、取消、重试能力。算法方面需要强化证据校验（不合规判定必须有原文证据支撑）、完善存疑策略、支持多问题拆分。

**审查结果与工作底稿（37 项）**：内测版的审查结果以扁平列表展示，正式版需要改为结构化展示——每个审核点可拆分为多个问题项，每个问题项包含独立的严重程度、结论判定、原文证据和整改建议。律师可以逐项修订结论和意见，标记确认状态（已确认/需复核/误报）。工作底稿需要支持版本管理和在线预览。证据溯源需要支持从审查结果点击跳转到原文对应位置。

**文档对比（18 项）**：对比任务需要接入权限体系，支持任务的命名、标签、删除和批量管理。对比结果需要完善分类展示（完全重复/高度相似/疑似抄袭）、原文定位和上下文查看。需要解决 OCR 乱码对对比结果的干扰，并支持对比报告导出。

**管理后台与工作台（31 项）**：需要新建管理后台，供管理员进行用户管理（创建/禁用/重置密码）、共享审核点和审核点库管理、异常任务处理（取消卡死任务、重试失败任务）。用户工作台需要按权限展示核心指标和待处理事项（转换失败、审查失败、待定稿等），侧边栏导航需要根据角色显示不同的功能入口。

**工程基础设施（21 项）**：支撑以上全部业务模块的底层工程改造。包括：数据模型全面重构（增加 Organization、User、Role、ResourceScope 等基础表，现有业务表增加归属字段）；全部 API 统一接入鉴权和权限校验；后台任务从进程内 BackgroundTasks 迁移到持久化任务队列，支持任务心跳、超时检测和故障恢复；建设统一的审计日志服务和错误码规范。同时需要编写数据迁移脚本，将内测版现有数据安全迁移到新的数据模型中。

> 其中 P0 项目（93 项）为正式版上线的最低要求，P1 项目（125 项）为律师日常使用所需的核心功能。各模块详细功能点清单见附件。
